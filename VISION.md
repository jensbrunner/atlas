## 1. PRODUCT GOALS AND NON-GOALS

### 1.1 Goals

- **Truth independent of prose.** Durable world facts, current state, character knowledge, and past statements have separate representations.
- **Causality and persistence.** World changes are validated, logged, replayable, and recoverable after process failure; actors have limited information and independent motives.
- **Player agency.** Accept free-form intent; never decide the player character's voluntary actions, thoughts, speech, or motives without permission.
- **Fair mechanics.** Transparent 2d6 adjudication, deterministic resource management, bounded tactical combat, and immutable recorded roll outcomes.
- **Meaningful improvisation.** The player may try unforeseen actions, which receive context-sensitive rulings grounded in available capabilities and physics.
- **Structural originality.** Track repeated plot architectures, not merely repeated words; proactively avoid unwanted tropes and trope drift.
- **Excellent narration.** Use a strong cloud model on work where it adds significant value; use small cloud/local models for repetitive structured tasks.
- **Mac-friendly.** Develop and run locally on Apple Silicon with 24 GB unified memory; local assistance must be optional, not mandatory.
- **Local-first privacy.** Campaign state lives locally by default; the user can back up, export, inspect, and erase it.
- **Testability.** End-to-end offline mode with an exact fake model; fixtures and deterministic replays.

### 1.2 Non-goals for v0.1

- Replicating the full D&D 5e ruleset or using licensed setting content.
- A full 3D world, voice chat, image generation, animation, or multiplayer.
- Running a frontier-scale model locally.
- A self-running society with thousands of fully simulated NPCs every minute.
- Automatic autonomous internet browsing during campaigns.
- Fully automatic correctness guarantees from AI-based critics; hard guarantees come from code.
- A giant multi-agent framework; the core orchestrator is ordinary, inspectable application logic.

### 1.3 What “better than a normal AI DM” means

Measured improvements in state integrity, continuity, player agency, originality, mechanical fairness, coherent NPC behavior, and sustained enjoyment over 100–500 turns. Do not claim superiority to skilled human DMs without blind user evaluations.

## 2. TECHNICAL STACK AND OPERATING CONSTRAINTS

### 2.1 Preferred stack

- Python >= 3.12; FastAPI; Pydantic v2; SQLAlchemy 2.x; Alembic.
- SQLite with foreign keys ON, WAL mode for a database on a **local disk**, and a bounded busy timeout. SQLite has one concurrent writer; use short transactions and optimistic campaign version checks.
- `pytest`, `pytest-asyncio`, `hypothesis` (property testing), `ruff`, and a type checker (mypy or pyright).
- `uv` for Python dependency management if installed; otherwise standard venv/pip with reproducible lock files.

- `httpx` for provider API access. Use official provider SDKs if they meaningfully simplify implementation, but hide them behind internal adapters.
- Provider targets: OpenAI Responses API; Ollama local API; optionally DeepSeek API for low-cost runtime roles.
- Local embeddings/semantic lookup later; SQLite FTS5 first. Do not make vector search a blocker for M0–M3.
- Structured, redacted logs (JSON or console in development); no raw secrets in logs.

### 2.2 Model IDs: defaults, not immutable truths

Configure model IDs via environment/settings, never bury them in code. If a user selects a cloud-dependent mode and credentials are absent, display a clear configuration error; do not silently change to a less capable paid model.

## 3. ARCHITECTURE AND TRUST BOUNDARIES

```
Player action
   |
FastAPI + ActionOrchestrator
   |-- load authoritative snapshot (DB)
   |-- IntentParser (fake/local/Luna)
   |-- retrieve relevant facts + actor knowledge
   |-- Adjudicator (rules, feasibility, dice, NPC policies)
   |-- calculate provisional events/outcome from version N
   |-- Narrator (Sol/Astra/local/fake) on allowlisted scene packet
   |-- Validators (schema, rules, canon, spoilers, agency)
   |-- atomic compare-and-swap commit if version still N
   |-- persist response and event batch
   '-- return committed narration + mechanics

Side services: campaign generator; trope fingerprinting; faction/world clock;
               retrieval; evaluations; provider router; export/backup.
```

**Critical separation:**

- **Domain code** is authorized to mutate authoritative state through validated commands/events.
- **Small models** propose intent, semantic interpretations, NPC deliberation, memory candidates, or critique. They have no direct database-write authority.
- **Narrator models** receive approved observable facts and resolved outcomes. They cannot alter rolls, invent important assets, expose secrets, or move the player's character.
- **Database** stores canonical state, event history, actor beliefs, scene descriptions, and model outputs with provenance.
- **Vector search and summaries** find information; neither overwrites the database or takes priority over exact state.

Every generated structured object must include a schema version and be validated. Do not treat a syntactically valid JSON result as semantically valid.

## 5. DATA MODEL: FOUR TYPES OF TRUTH

1. **Canon:** historical or immutable established facts, e.g. which organization built a bridge.
2. **World state:** mutable current conditions, e.g. bridge structural integrity, character health, current time.
3. **Epistemic state:** what each character believes, knows, suspects, or has heard; may be false.
4. **Narrative record:** what was said/described to the player, with speaker and perspective, but not automatically true.

Additional classification: `PUBLIC`, `GM_ONLY`, `ACTOR_PRIVATE`, `PLAYER_KNOWN`. Actor knowledge is its own per-actor relation, not just a global visibility flag. A fact may be true yet unavailable to the player; a statement may be known but untrue.

### 5.1 Stable identifiers

Use ULIDs or UUIDs for campaigns, turns, characters, places, items, facts, and events. Human-readable slugs are optional; never use names as primary identifiers. Track aliases and renames.

### 5.2 Minimum relational tables

- `campaigns(id, title, rules_version, status, state_version, current_time, seed, settings_json, created_at, updated_at)`.
- `turns(id, campaign_id, client_action_id, ordinal, player_text, status, snapshot_version, narrator_text, mechanics_json, error_code, created_at, committed_at)`; unique `(campaign_id, client_action_id)` and `(campaign_id, ordinal)`.
- `events(id, campaign_id, turn_id, seq, type, actor_id, subject_id, payload_json, inverse_json_optional, occurred_at_world, created_at, schema_version, provenance_json)`; append-only, unique `(campaign_id, seq)`.
- `entities(id, campaign_id, kind, slug, display_name, static_json, created_event_id, retired_event_id)`.
- `entity_state(entity_id, campaign_id, version, state_json)`; strictly an event-derived projection.
- `facts(id, campaign_id, subject_id, predicate, object_json, canonical_status, valid_from_event, valid_to_event, source_event_id, sensitivity)`.
- `knowledge(actor_id, fact_id, belief_status, confidence, acquired_event_id, retracted_event_id)`; assertions can be known, suspected, disputed, or mistaken.
- `statements(id, campaign_id, turn_id, speaker_id, audience_json, proposition_json, content_text, truth_claim_status, linked_fact_id_nullable)`.
- `relationships(id, campaign_id, actor_a, actor_b, relation_type, strength, updated_event_id)`.
- `items(id, campaign_id, definition_json, owner_id_nullable, location_id_nullable, quantity, state_json, version)`; do not allow contradictory owners/locations.
- `locations(id, campaign_id, parent_id_nullable, topology_json, public_description, gm_description, state_json)`.
- `npc_goals(id, npc_id, objective_json, priority, status, known_constraints_json, plan_json)`.
- `factions(id, campaign_id, state_json)` and `clocks(id, campaign_id, owner_id, segments, filled, trigger_json, visibility, state)`.
- `rolls(id, campaign_id, turn_id, label, formula_json, rng_algorithm, seed_ref, result_json, visibility)`.
- `scenes(id, campaign_id, status, location_id, participant_ids_json, public_observations_json, material_details_json)`.
- `narrative_fingerprints(id, campaign_id, arc_id, features_json, embedding_ref_nullable, novelty_score_nullable, created_at)`.
- `player_preferences(campaign_id, hard_avoids_json, soft_avoids_json, favorite_activities_json, prose_style_json, updated_at)`.
- `model_calls(id, turn_id_nullable, role, provider, model_id, latency_ms, input_tokens, output_tokens, estimated_cost_usd, success, error_code, created_at)`; no unnecessary raw personal text in telemetry.
- `checkpoints(id, campaign_id, event_seq, state_hash, snapshot_json, created_at)`.

Use Alembic migrations. Add foreign keys, uniqueness constraints, enumerations at the schema layer, and indexes for `(campaign_id, seq)`, `(campaign_id, state_version)`, entity lookups, turn order, fact subject, and actor knowledge. Prefer normalized core fields and bounded JSON metadata rather than placing the whole game into one opaque JSON blob.

Use integer world-time ticks/minutes from campaign epoch, not naive date strings internally. Human-readable dates are derived for narration. The event `sequence` is monotonic per campaign. A model must never invent event sequence numbers.

### 5.4 Strong invariants

- No negative inventories, health beyond allowed bounds, duplicated unique items, or invalid clocks.
- A living actor must have one coherent physical location unless the rules explicitly allow otherwise.
- Actor actions require appropriate capability, resources, and knowledge.
- Facts never become canon just because an NPC says them or a model summarizes them.
- Immutable historical records are not silently rewritten; corrections are explicit events or deliberate branch/retcon operations.
- Dice and costs for a completed turn cannot be changed by retries.
- Player agency: no voluntary player action without a player command or explicit delegated authority.
- Narrator cannot authoritatively disclose `GM_ONLY` secrets outside an authorized reveal.
- Every material prop/location introduced in player-facing prose must correspond to a preexisting or approved new entity/detail.
- No direct editing of the event ledger after commit; integrity repairs are auditable compensating operations.

## 6. TURN PROCESSING: CORRECTNESS BEFORE PROSE

### 6.1 Lifecycle

`RECEIVED -> PARSED -> RESOLVED -> NARRATED -> VALIDATED -> COMMITTED` or `FAILED`.

`RECEIVED` records the original intent and client idempotency key. A failed action that has not committed state may be retried safely. `COMMITTED` responses are immutable and returned verbatim on repeated requests with the same key.

### 6.2 Required algorithm

1. Accept `POST /api/v1/campaigns/{id}/turns` with `client_action_id` (UUID) and `player_text`.
2. If the key already exists and is committed, return its saved outcome. If processing, return an explicit pending/conflict response rather than creating a duplicate.
3. Snapshot canonical state at campaign version `V`; record a durable processing attempt and cryptographic roll seed/token in a short transaction.
4. Parse player intent into structured `IntentProposal`: actor, action, targets, declared speech, stated goal, tool/item references, ambiguity flags. An ambiguous parsing model must not choose a materially different action.
5. Retrieve exact related entities/facts, current scene, rules, actor knowledge, clocks, and relevant history. Prepare a restricted context packet.
6. Run hard feasibility checks. Resolve automatic successes/failures without dice when appropriate; use deterministic dice only when risk and uncertainty justify them.
7. Generate an `OutcomeProposal` with provisional events, public observations, costs, time advancement, possible clocks, and a mechanical record. The deterministic rules engine must be the final authority.
8. Validate proposed events against the `V` snapshot: foreign keys, resources, state preconditions, time, agency, knowledge, capabilities, causal requirements, and allowed event types.
9. Build `NarrationPacket` from approved observable state and the outcome. Request text from selected narrator. Narrator must not see unrelated secrets.
10. Validate response: consistency, unauthorized material facts, forbidden spoilers, player agency, tone and trope policies. Validate any new material-detail proposals before accepting them.
11. If valid, acquire a short DB transaction; compare campaign `state_version == V`. Atomically insert events/rolls/turn response, update projections, increment version, and mark turn `COMMITTED`. On version mismatch: re-evaluate from current state using the same action identity; never merge conflicting events blindly.
12. Return saved narrative, mechanics, turn ID, committed version, and optional UI changes. Stream only the **committed and validated** response in v0.1.

**Do not keep an SQLite write transaction open while waiting for an LLM.** Use optimistic concurrency. On crashes, resume or fail pending turns without applying uncommitted effects. Store enough input and roll seed information to replay adjudication. Each turn has one authoritative commit.

### 6.3 Deterministic randomness

Use OS randomness to generate a per-turn secret seed, store it with the attempt, and expand it with a stable documented HMAC-SHA256/counter algorithm or another explicitly versioned reproducible RNG. Avoid using an undefined model-simulated die. Use unbiased bounded sampling. Store rolls as immutable outcomes; optionally reveal a receipt after resolution. Unit test fixed-seed sequences and distribution sanity. Roll outcomes should not be streamed until the turn is committed.

## 7. RULES: ATLAS CORE v0.1

### 7.1 Core resolution

Use `2d6 + ability + training - difficulty` (integer arithmetic).

- `<= 6`: failure with proportionate established consequence.
- `7..9`: success with cost, complication, limited effect, or difficult choice.
- `>= 10`: clean success at the intended reasonable scale.

Initial design bounds: ability `-1..+2`, training `0..+2`, difficulty `0..3`. These are provisional, not mathematically balanced. Publish the exact distribution table and playtest before final tuning. Do not penalize routine actions with rolls.

### 7.2 Attributes and resources

Start with four attributes: `Might`, `Agility`, `Insight`, `Presence`. Characters also have a few skills, `health`, `stress`, `supplies`, `currency`, equipment slots, and explicit abilities. NPCs use the same simplified resolution rules. Starting character templates must be viable without a large character-building workflow.

### 7.3 Stakes-first adjudication

Before rolling, determine and, where natural, communicate: intent, established fictional position, plausibility, risk, effect scale, and consequences. No retroactive escalation solely because the outcome was convenient. An impossible action remains impossible unless an established ability permits it. On mixed success, give a cost that follows from the scene, not a generic random punishment.

### 7.4 Combat and hazards

Use a small zone graph instead of a mandatory grid. Each zone stores occupants, connections, cover, elevation, hazards, and interactable objects. Turns: player acts, relevant enemies respond according to initiative/tactical rules, clocks update. Attacks use same core resolution with clear effect/damage tables. Track armor, health, stress, conditions, and objectives. Enemies may flee, surrender, defend, bargain, or reposition; do not assume all fights end in death. Track who can see or reach which zone. Add detailed combat only after social/exploration turns are stable.

### 7.5 Time and world simulation

Use integer world-minute ticks. Each meaningful action consumes time; resting and travel advance schedules and clocks. Nearby active NPCs have high-fidelity state; distant factions update through scheduled events. Time advancement executes only rules-valid queued events. Offline wall-clock time does not advance the game unless the user enables such a mode (not v0.1).

### 7.6 Consequences and endings

Allow persistent injuries, loss of property, failed quests, hostile factions, missed deadlines, character death where opted into the difficulty settings, and real campaign endings. Do not turn every failure into progress or every arc into a cliffhanger. Record player-configured tone and difficulty. Bound consequences to declared stakes and game rules.

## 8. NPC AGENCY, KNOWLEDGE, AND FACTION CLOCKS

Important NPCs need persistent goals, constraints, resources, obligations, fears, personality tendencies, relationships, and a knowledge set. They also have a current plan and an explanation of what they are likely to do if the player intervenes or does nothing.

A `NpcDecisionProposal` may be generated by a small model, but receives only what the NPC could know. Code checks the proposed behavior against resources, current location, physical constraints, loyalties, and actual state. For pivotal negotiation or moral dilemmas, escalate to a stronger model.

Define faction `Clock(segments, filled, trigger, owner, visibility)` and scheduled actions. A clock advances only because of specific valid events or passage of relevant time, not because the narrative needs urgency. Do not advance unseen world factions on every word or chat message; use time and causality.

Minimum NPC test: an NPC tells a deliberate lie; the player records it; another NPC repeats the rumor; the underlying canon remains unchanged; a third NPC lacking access to the rumor does not know it.

## 9. MEMORY AND KNOWLEDGE FIREWALL

### 9.1 Retrieval hierarchy

1. Exact campaign/scene/player state (always).
2. Exact entity references and names from player intent.
3. Authoritative relevant facts and knowledge filtered by viewpoint.
4. Active clocks, consequences, promises, and recent event timeline.
5. FTS5 search over past conversations and event descriptions.
6. Optional local embedding search for indirect thematic relevance.
7. A session summary for orientation only, never truth authority.

Prioritize recency and causal relevance without suppressing old pinned commitments. Each retrieved record must carry stable entity/event/fact IDs and visibility restrictions.

### 9.2 Memory ingestion

A local/Luna extractor may suggest `statement`, `observation`, `fact_candidate`, `relationship_candidate`, or `preference_candidate`. Do not directly store a candidate as a canonical truth. Canon promotion requires a source event or explicit authorized world-authoring operation. Preserve conflicting reports and uncertainty. Link statements to who said them and who heard them.

### 9.3 Knowledge firewall

Construct separate context views: `GM`, `NPC(actor_id)`, and `PLAYER_NARRATOR`. Never send full GM secrets to a model asked to speak as a specific NPC. A narrator may receive tightly scoped secret reveal instructions only when a reveal event has been authorized. Test by planting a unique secret marker in GM-only data and asserting that ordinary narration never contains it.

### 9.4 Context budget

Retrieve compact, typed context. Maintain a clear token budget per role; do not paste full chat history or full encyclopedia into every turn. Make cache-friendly stable instructions a provider optimization only. Store context-build audit metadata so a continuity failure can be investigated.

## 10. NARRATIVE DIVERSITY AND ANTI-REPETITION ENGINE

### 10.1 Structural fingerprint

For each adventure and significant arc, record:

- primary gameplay activity (`exploration`, `negotiation`, `heist`, `defense`, `hunt`, `survival`, `tournament`, `politics`, `expedition`, etc.);
- conflict architecture and initiating event;
- antagonist/faction motivations;
- types of player decisions and possible resolutions;
- stakes, time pressure, and failure modes;
- setting function (quest hub, dungeon, frontier, travel route, arena, etc.);
- plot devices, twist mechanisms, sensory motifs, and repeated phrases;
- supernatural intensity, horror intensity, and intended tone.

### 10.2 Candidate generation

Generate 8–12 **short** structurally diverse outline candidates, not 8–12 full adventures. First filter on hard player preferences, genre, and mechanical playability. Compute similarity to prior arc fingerprints using interpretable categorical overlap plus optional semantic embeddings. Reject near-duplicates and propose a shortlist with explanations. Develop the selected candidate into a scenario with persistent NPC motives, locations, causal timelines, objectives, clocks, and possible failure states. Never determine a single mandatory resolution.

### 10.3 Example preference defaults

For a player who complained about repeated haunted-village stories:

```json
{
  "hard_avoid": ["bell_as_supernatural_omen", "missing_relative_backstory"],
  "soft_avoid": ["ancient_cult", "haunted_monastery", "isolated_fog_village"],
  "positive_targets": ["concrete_choices", "classic_fantasy", "material_conflict", "exploration"]
}
```

Store preferences with scope (`campaign` or `player_profile`) and make them editable. Do not automatically forbid all tropes for everyone. Do not conflate an isolated bell sound with a whole occult-investigation structure; evaluate motifs and deeper plots separately.

### 10.4 Anti-drift checks

On major new plot beats (not every conversational sentence), check whether a new artifact/cult/prophecy/secret society/etc. is causally motivated by established facts and consistent with the existing scenario. A human or player can opt into a different genre; otherwise unexpected genre drift is flagged. A novelty audit is an advisory design gate; it cannot arbitrarily rewrite already committed events or reveal hidden twists to the player.

### 10.5 Evaluation protocol

Run 50–100 independent adventure seeds for a baseline direct-DM prompt and the ATLAS generation pipeline. Compare structural fingerprint distributions, near-duplicate rates, activity diversity, and blind player ratings. Validate that a novelty checker identifies renamed versions of the same haunted-village story. Report false positives too: originality must not become forced incoherence.

## 11. FRONTIER NARRATION CONTRACT

### 11.1 Narrator input

Supply: current public scene, sensory facts, participants, actor-viewpoint knowledge, validated outcome, authorized dialogue/behavior, style/length preferences, player action, and precise list of permitted material revelations. Never supply all undiscovered secrets. Use stable IDs internally but render names naturally.

### 11.2 Narrator rules

- Describe only what the player can perceive, infer, remember, or has explicitly been told.
- Never dictate the player's voluntary next move, speech, feelings, beliefs, or internal motivations.
- Never contradict a committed mechanical outcome.
- Do not invent new major NPCs, items, locations, abilities, lore, quest objectives, or reveals inside prose. Propose any material addition as a separately validated scene detail.
- Vary pacing; not every scene needs mystery, danger, dramatic sentence fragments, or a cliffhanger.
- Prefer concrete, actionable sensory information and believable dialogue over abstract portents.
- End where player agency resumes. Do not always offer a menu; free-form input is primary.
- NPCs should retain distinctive motives, speech habits, and limits; do not make them automatically agree with the player.
- Honor campaign tone and trope constraints.

### 11.3 Material detail policy

Separate `cosmetic_detail` (weather adjectives, clothing texture) from `material_detail` (a door, key, weapon, person, exit, clue, or movable object). Material details must be registered in the scene before publication. If an earlier cosmetic detail becomes interactable, promote it through a validated `scene.detail_established` event without contradiciting previous prose. Do not deny an explicitly described object exists just because it was not in the database.

### 11.4 Verification strategy

Hard checks use entity IDs, allowed outcome atoms, spoiler set, state diffs, character action permissions, and deterministic predicates. A secondary model can flag soft issues (out-of-character speech, repetitive prose, implausible consequences), but the system must distinguish a critic warning from a proven invariant breach. Cap retries (e.g. two corrective attempts); fail gracefully with a non-mutating error or approved deterministic fallback if validation cannot pass.

## 12. MODEL GATEWAY AND ROUTING

### 12.1 Interface

Expose a provider-neutral async interface (Python typing/Protocol) similar to:

```python
class ModelGateway(Protocol):
    async def generate_text(
        self, role: str, messages: list[dict], *, budget: dict
    ) -> "TextResult": ...
    async def generate_structured(
        self, role: str, messages: list[dict], schema: type, *, budget: dict
    ) -> "StructuredResult": ...
```

Results include provider/model ID, content, token usage if available, elapsed time, and failure classification. Providers should implement capability flags (JSON-schema output, JSON-object output, tool calling, streaming, context size). Do not force identical vendor APIs behind leaky assumptions.

### 12.2 Provider roles

- `intent_parser`: fake -> local Qwen3 8B / OpenAI Luna.
- `memory_extractor`: fake -> local / Luna.
- `npc_reasoner`: rules first -> Luna / stronger model if unresolved.
- `outline_generator`: Luna/local; frontier for final scenario construction.
- `narrator`: Sol, optionally Astra; local/fake fallback mode.
- `semantic_critic`: local/Luna as an advisory service.

Never add an LLM call if deterministic code can answer the question. No routine debate among several agents.

### 12.3 Structured outputs and failures

Ollama supports JSON-schema-constrained output; OpenAI supports structured JSON-schema outputs; DeepSeek exposes JSON-object mode for Chat Completions and JSON-schema output on certain Responses API paths. **Verify the exact chosen endpoint and model capabilities at implementation time.** All outputs are validated with Pydantic; empty content, schema mismatch, refusal, truncation, timeout, rate limits, and provider outage are distinct error types. Do not try to parse arbitrary prose as trusted commands. Retry carefully with bounded attempts and no duplicate state mutation.

### 12.4 Cost and latency

Store per-call usage, provider, role, and inferred USD cost with a configurable pricing table and revision date; unknown pricing must be marked unknown rather than zero. Enforce request/session/month budgets, maximum parallel calls, token limits, and timeouts. Use circuit breakers and explicit provider fallbacks, never unexpected premium escalation. No paid live calls in offline tests. Prefer concurrent independent preparation; keep sequential critical-path calls minimal.

Use `/api/v1` and OpenAPI-generated schemas.

- `GET /healthz` -> app/database status; no paid model calls.

- `GET /api/v1/campaigns/{id}/turns/{turn_id}` -> authoritative status/outcome.
- `GET /api/v1/campaigns/{id}/journal` -> only player-known facts/statements/events.
- `POST /api/v1/campaigns/{id}/save-checkpoint` -> snapshot/checkpoint, optional manual trigger.
- `GET /api/v1/campaigns/{id}/export` -> downloadable versioned campaign archive.
- `POST /api/v1/campaigns/{id}/preferences` -> update tone/avoidances with explicit validation.


Response fields: `turn_id`, `status`, `campaign_version`, `narration`, `mechanics`, `elapsed_world_minutes`, `public_event_ids`, `ui_state_patch`, `cost_estimate_usd`. ## 15. FIRST PLAYABLE ADVENTURE FIXTURE

Create a **non-horror** classic-fantasy scenario named **The Broken Span**. Its purpose is to prove that ATLAS supports concrete choices without cults, undead, prophecy, mysterious bells, or generic missing-person hooks.

### Setup

A town has reused three sacred engineering stones from a stone giant's ancestral bridge in its flood defenses. The giant demands their return before a storm. The flood defense will fail if the stones are simply removed. Both parties have legitimate stakes; no single mandated resolution exists.

### Minimum entities

- Player character with health, supplies, money, four attributes, training, and starting equipment.
- Stone giant with a goal, limitations, location, and negotiating conditions.
- Town magistrate with grain/security concerns and incomplete information.
- Dwarven engineer who knows replacement options but lacks materials.
- Mercenary captain concerned about pay and survival.
- Two factions: town council and caravan guild.
- Locations: town square, flood gate, old bridge, quarry, workshop, north road.
- Inventory: stones, timber, tools, coins, supplies, repair materials.
- Clocks: storm arrival, giant's deadline, town unrest.
- Secret: a caravan knows of an alternative source of suitable stone; only the caravan leader initially knows.

### Supported solutions

Negotiation, engineering, fundraising, trade, expeditions for materials, opportunistic deception, partial compromise, combat, abandonment, or failure. Do not special-case a predetermined “correct” path. Include at least one NPC misconception and one intentionally dishonest statement to exercise knowledge tracking.

### Acceptance scenario

Player asks what can replace the stones; learns an actionable lead; investigates the quarry; spends supplies and time; acquires materials; attempts a repair; outcome changes the world; after restart, every resource, NPC belief, clock, and discovery remains correct. A very different player can instead antagonize the giant and cause a different persistent outcome.

## 16. TESTING STRATEGY

### 16.1 Unit tests, required before any API model integration

- Dice reproducibility from fixed seeds, correct modifier/difficulty application, probability/distribution sanity.
- Exact resource accounting: use, move, split, consume, heal, damage, purchase; no double-spend.
- Event schema validation and reject-unknown-event behavior.
- Projection replay equality: replay from genesis matches live projection hash.
- Knowledge isolation: statements do not imply canonical truth; secrets stay restricted.
- Time and clock triggers: advance only under correct conditions; avoid double-firing.
- Strict player-agency checks: parser/narrator cannot invent a voluntary player action.
- Idempotency: duplicate `client_action_id` yields exactly one committed event batch and same saved output.
- Concurrency: conflicting expected versions do not both commit.
- Recovery: simulate crash at each lifecycle phase; no partial world changes.
- Backup/export/import: round trip preserves hashes, schema version, and hidden/public separation.

### 16.2 Integration tests

- FastAPI + temporary SQLite DB with migrations.
- Entire `Player text -> parsed intent -> outcome -> events -> narration -> commit` pipeline using fake models.
- Fake model emits hallucinated key, NPC, clue, player action, or secret: validation rejects it.
- Fake model times out or returns bad JSON: turn is not partially applied.
- Reopen DB after 100 scripted turns; verify exact state and every promise/clock.
- Journal endpoint never includes undiscovered secret fixture markers.
- Optional live provider contract tests guarded by environment and spending cap.

### 16.3 Property-based and fuzz tests

Using Hypothesis where appropriate, generate sequences of inventory transfers, combat damage, time updates, canceled requests, version conflicts, and NPC knowledge claims. Assert hard invariants after every committed event. Use bounded seeds and save failing examples as regression fixtures.

### 16.4 Narrative evaluations (later phases)

- Compare 50–100 independent campaign outlines to baseline direct-LLM outputs for structural similarity.
- Explicit Bell Test: 10 renamed occult-village scenarios must be grouped as similar despite different names and imagery.
- Genre Test: requests for classic fantasy do not silently switch to dark horror.
- Agency Test: narrator must not move/speak/decide for player.
- Continuity Test: commitments and NPC beliefs remembered across 300 and 500 turns.
- Calibration Test: critical clues do not appear only because the player suggests them.
- Human blind evaluations of playability, dialogue, consequence quality, originality, pacing, and overall fun.

### 16.5 Targets, not achieved claims

- 100% hard-invariant compliance in test suite.
- Zero duplicate commits and zero secret leaks in controlled fixtures.
- >=99% correct retrieval for manually curated critical facts in long-horizon evals (stretch target).
- Statistically meaningful reduction in structural near-duplicates versus baseline (method and threshold must be specified before evaluation).
- Strong subjective player preference versus a direct chatbot baseline. No claims of human-DM superiority until tested.

## 17. SECURITY, PRIVACY, AND OPERATIONS

- Campaign data local by default; never upload full campaign archives implicitly.
- Provide an explicit cloud inference consent control and indicate which scene/fact fields are transmitted to which provider.
- Keep API keys outside database and source control; redact request headers, raw key material, and GM secrets from routine logs.
- Treat all user text, imported campaign materials, model text, and retrieved documents as untrusted. They cannot issue arbitrary filesystem, SQL, network, or shell commands. No model-generated SQL execution.
- Use typed allowed domain commands and strict event schemas. Validate IDs are within the campaign and access scope.
- Mitigate prompt injection by separating instructions from narrative content, rejecting attempts by in-game text to override runtime constraints, and using rule-based authority boundaries.
- Enforce per-request limits, budgets, timeouts, and content bounds.
- Use regular integrity checks, SQLite backups, versioned exports, and migrations. Avoid writing SQLite WAL to shared/network filesystems.
- Provide an explicit delete-campaign operation only after confirmation; support local data deletion and export.
- Log model call metadata and user-visible error codes; retain minimal content required for debugging.
- Build for a single local user first; if adding remote authentication later, design a separate security review.

## 18. PERFORMANCE AND QUALITY BUDGETS

Initial performance targets (measure; do not promise blindly):

- Offline fake-model core turn: p95 < 250 ms on development hardware.
- Local extraction model: target reasonable responsiveness; benchmark on the actual 24 GB Mac rather than guessing.
- Balanced cloud narrative turn: aspirational p50 < 8 s, p95 < 20 s excluding provider outages; show a processing state.
- Default typical scene packet < 8,000 input tokens, preferably much smaller; allow larger packets for genuinely complex scenes under configured limits.
- One semantic parser call + one narrator call on ordinary turns. Additional model calls only for exceptional adjudications/validation issues.
- No extra model calls to calculate dice, check inventory, tell time, or load facts.
- Maintain a cost ledger and show estimated session spending, including uncertainty where providers omit usage.

Instrument phase timings: snapshot, parsing, retrieval, adjudication, narration, validation, commit. Track error rates, continuity failures, provider retries, novelty rejections, and spending per mode. Never use synthetic benchmark claims as production measurements.

## 21. DESIGN DECISIONS THAT MUST NOT REGRESS

1. **Never use chat history as canonical world state.** Store state/events in SQLite.
2. **Never let a narrator directly change inventory, time, facts, quests, dice, or NPC knowledge.** It may propose details under rules.
3. **Never let speculative story beats override established causes.** Creative planning happens within the world model.
4. **Never assume each NPC shares GM knowledge.** Restrict NPC model contexts.
5. **Never confuse a statement with a fact.** Track source and audience.
6. **Never let retry/replay reroll a committed result.** Persist idempotency keys and rolls.
7. **Never force a player decision because a dramatic scene requires it.** Ask when intention is genuinely ambiguous.
8. **Never rely on a model critic as the only validator for hard invariants.** Enforce them in domain code.
9. **Never overfit novelty to surface nouns.** Compare conflict and player experience structure.
10. **Never invent prices, model capabilities, benchmarks, or completed test results.** Verify and label assumptions.
11. **Never add expensive inference to mundane deterministic operations.** Favor cheap local/code routes.
12. **Never sacrifice playability for architectural completeness.** Ship the first persistent offline scenario early.
